# 실행 흐름

분석 → 설계·구현 기록 준비 → 구현 승인 → 구현·결과 수용 → 검증·리뷰 → 기록·stage·보고 순서로 진행한다. 이미 완료된 단계와 기존 승인은 반복하지 않는다.

## 1. 현재 상태와 요구사항

- 프로젝트 규칙, 작업 경로, branch/HEAD, staged·unstaged·untracked 변경을 확인한다. 수정 예상 경로는 기존 diff도 확인해 이번 변경과 구분한다.
- 요구사항·제외 범위·완료 조건을 파악하고 실제 호출 흐름, 계약, 실패 경로와 영향을 읽는다.
- Task 번호는 [로드맵](../templates/roadmap.md)이 발급한다. 로드맵에 없는 작업은 문서 준비 단계에서 행을 추가하며, 번호 때문에 분석을 지연하지 않는다. 작성자는 사용자 제공 정보를 활용한다.
- 문서 위치·템플릿이 없을 때만 [setup](setup-guide.md)을 읽는다. 관련 없는 외부 서비스 연결은 확인하지 않는다.

## 2. 문서 준비와 승인

[plan](../templates/plan.md)에는 계약·설계 이유·위험을, [impl](../templates/implementation.md)에는 파일별 TODO·완료 조건·검증 계획을 작성한다. 상세 코드 대신 변경 위치, 입출력 계약과 실패 조건을 명시한다. 판단을 설명하는 비채택안과 다이어그램만 포함한다.

| 현재 승인 상태 | 다음 행동 |
|---|---|
| 설계·TODO·검증안까지 구현 승인됨 | 승인 근거와 범위를 기록하고 진행. impl 미작성 시 먼저 보완하며 재승인은 받지 않음 |
| 설계만 승인됨 | TODO·검증안을 준비해 구현 승인 요청 |
| 설계 선택 미확정 | 선택의 영향과 확인 필요 항목을 제시해 설계부터 확정 |
| 아직 승인 없음, 두 문서 준비 가능 | 설계·TODO·검증안을 함께 제시해 구현 승인 한 번 요청 |

승인은 `impl` 현재 상태에 시각·사용자 메시지 요지·적용 범위로 기록한다. 설계만 있는 단계의 승인은 plan에 두고 impl에서 참조한다. 요청된 단계가 문서 작성까지만이면 여기서 보고한다.

plan/impl을 처음 만들 때 [로드맵](../templates/roadmap.md)에 행을 추가한다. 이미 등록된 Task는 상태만 바꾼다. 파일이 없으면 템플릿으로 만든다. 상태는 승인 전 `예정`, 구현 착수 `진행`, 개발·검증 완료 `완료`, 중단 시 `보류`·`차단`으로 바꾼다. commit을 하거나 확인하면 해시를 비고에 적는다. 로드맵은 목록용이다. 현재 상태의 기준은 impl이며, 로드맵에 상세 증거를 복제하지 않는다.

## 3. 구현과 결과 수용

직접 수행 또는 [SubAgent 위임](subagent-delegation-guide.md)을 선택한다. 위임 여부와 병렬 실행 여부는 별개다.

TODO를 수용할 때 실제 변경, 중요한 결정, 검증 결과 또는 미검증 사유를 impl에 남긴다. 그 TODO에 의존하는 후속 작업은 수용 기록 후 시작한다. 독립 TODO는 병렬 실행할 수 있으며 전역 순차 기록 때문에 서로를 기다리지 않는다. 병렬 결과는 부모가 도착한 결과별로 수용·기록한다.

구현 뒤 [검증·리뷰 기준](verification-guide.md)을 적용한다. 승인된 동작을 회복하는 수정과 재검증은 현재 승인으로 진행한다.

## 4. 중단과 재승인

| 발견한 내용 | 처리 |
|---|---|
| 승인된 계약을 어긴 구현/테스트 결함, 범위 안의 Critical finding | 해당 결과 수용과 의존 작업 진행을 막고 수정·재검증·재리뷰. 심각도 이름만으로 사용자 재승인을 요구하지 않음 |
| 승인 계약을 유지하는 세부 구현 변경, 필요한 관련 테스트 파일 추가 | 부모가 영향·소유권 확인 후 TODO를 보완하고 기록. 사용자 지정 파일 제한은 준수 |
| 요구사항·제외 범위 변경, 새 DB/외부 API/권한 계약 또는 운영 위험, 검증·보호 수준의 실질적 축소 | 영향받는 작업을 멈추고 plan의 변경 이유·영향·대안을 준비한 뒤 사용자 재승인 |
| 데이터 손실·파괴적 조치, 승인되지 않은 외부 쓰기 등 기존 권한 밖 행동 | 해당 행동을 실행하지 않고 구체적 결과/대안을 준비해 필요한 승인 요청 |
| 환경·도구 오류 | 원인을 분리하고 허용된 대체 검증 수행. 필요한 증거를 얻지 못하면 미완료로 기록 |
| 리뷰 기준 파일 부재 | verification 가이드의 대체 기준으로 검토. 중요한 계약 자체가 불명확하면 그 부분만 확인 |

하위 Agent는 배정된 쓰기 범위를 스스로 넓히지 않고 부모에게 보고한다. 부모는 위 표로 범위 내 조정인지 재승인 대상인지 판단한다. 설계 변경 때문에 의존 작업이 잘못된 계약으로 계속 실행되지 않도록 중지하되, 영향 없는 승인 작업은 계속할 수 있다. 이력에는 변경 이유와 시각을 남기고 과거 승인을 소급해 바꾸지 않는다.

## 5. 보고 전 stage

설계/구현 승인 요청, 수용한 단계 완료, 개발 완료, 승인된 보관 이동을 보고하기 전에 그 단위의 변경을 stage한다. 단순 진행 상황 메시지는 이 게이트가 아니다.

1. 대상 경로의 작업자가 쓰기를 끝냈는지 확인하고 실제 diff를 검토한다.
2. 기존 index와 worktree 변경을 비교해 이번 작업 소유 변경을 식별한다.
3. 파일 전체가 이번 작업 변경이면 `git add -- <명시적 파일 경로>`를 사용한다.
4. 같은 파일에 기존 사용자 변경이 섞였으면 이번 작업의 hunk만 stage한다. 분리가 불명확하면 그 파일은 보류하고 이유를 보고한다. 기존 staged hunk를 해제하거나 덮어쓰지 않는다. 로드맵은 여러 작업이 같이 고치는 파일이므로 이번 작업의 행만 stage한다.
5. `git diff --cached -- <대상 경로>`, `git diff --cached --check -- <대상 경로>`, `git status --short`로 실제 staged 내용과 남은 변경을 확인한다.

`git add .`/`git add -A`/광범위 디렉터리 stage는 하지 않는다. 시크릿은 stage하지 않는다. commit/push는 사용자 명시 요청이 있을 때만 한다. 비 Git 디렉터리, 권한 오류, 혼합 hunk로 stage 불가하면 안전한 나머지 작업을 끝내고 상태를 보고한다. stage 실패를 숨기거나 검증 실패를 완료로 표시하지 않는다.

## 6. 외부 업데이트

API 변경이 있으면 반영 내용을 준비한다. API 발견·인증 성공은 쓰기 승인이 아니다. 해당 DDD 작업의 원 요청 또는 후속 승인에 대상 쓰기가 포함되고 인증 가능한 경우에만 실행한다. 이미 받은 승인 범위는 다시 묻지 않는다.

- API 변경은 [API 가이드](api-documentation-guide.md)에 따라 실제 구현과 명세를 대조한다.
- 프로젝트가 외부 이슈 트래커를 함께 쓰면 그 프로젝트 규칙을 따른다. 작업 상태의 기준은 로드맵이며, 외부 트래커 반영에도 같은 쓰기 승인 기준을 적용한다.
- 인증/권한 오류는 원인과 필요한 조치를 기록한다. 인증 우회나 같은 실패의 반복 호출은 하지 않는다.
- impl 후속 결과에 실제 반영 근거, 승인 대기 또는 실패를 기록한다. 승인 대기인 외부 작업을 완료로 세지 않는다. 외부 API를 호출하는 담당도 부모가 통제한다.

## 7. 완료와 보관

완료 보고 전 다음을 확인한다.

- 승인된 TODO가 수용됐고 최종 변경에 유효한 검증·리뷰 증거가 있다.
- 차단 finding은 해결됐다. 환경 차단, 미실행 검증, 운영 후속은 결과와 구분된다.
- 관련 외부 반영·지식화의 결과 또는 남은 일이 기록됐다.
- 이번 변경의 stage 내용이 확인됐거나 불가 사유가 있다.
- impl 현재 상태에 개발·검증·외부 반영·Git 상태·다음 행동이 일치한다.
- 로드맵 행의 상태·문서 링크·commit이 impl 현재 상태와 일치한다.

`개발 완료`는 자동으로 commit, 배포, 문서 보관 완료를 뜻하지 않는다. 필수 검증이 막혔으면 `구현 완료 / 검증 미완료`처럼 범위를 나누어 보고하고 DDD 작업 전체를 완료로 표시하지 않는다. 별도 문서는 [기록 위치](record-routing-guide.md)에 따라 필요한 경우만 만든다.

사용자가 완료 처리/Task 종료/completed 이동을 요청하거나 승인한 경우에만 관련 문서를 같은 파일명으로 `completed/`에 옮긴다. 상호 링크, 로드맵의 문서 링크, 외부 참조를 확인하고 이동·링크 수정도 stage한다. `troubleshooting/`, `tech_notes/`, `templates/`는 이동하지 않는다.

## 8. 재개와 컨텍스트 복원

1. 프로젝트 규칙, plan의 승인 계약, impl의 현재 상태·관련 증거를 읽는다. 진행 중인 작업 목록은 로드맵에서 찾을 수 있다. 이력 전체는 필요한 판단이 있을 때만 조회한다.
2. 실제 cwd/branch/HEAD, index/worktree diff, 실행 중 Agent·프로세스를 확인한다. 문서의 과거 PASS나 stage 상태를 현재 상태로 간주하지 않는다.
3. 기록 이후 코드·테스트·환경 변경이 검증에 미친 영향을 판단한다. 유효한 증거는 재사용하고 바뀐 범위는 다시 검증한다.
4. 종료가 불명확한 작업자의 소유 경로는 재배정하지 않는다. 실제 상태를 확인한 뒤 현재 상태와 다음 TODO를 갱신한다.
