# 기록 위치와 중복 방지

현재 상태와 과거 사건을 구분하고, 상세 증거는 한 곳에 둔다. 기존 프로젝트 기록을 일괄 변환할 필요는 없으며 진행 중인 작업에서 필요한 부분부터 적용한다.

## 기록의 소유 위치

| 내용 | 주 기록 |
|---|---|
| 요구사항·제외 범위·채택 계약·설계 이유·설계 변경 | plan |
| 현재 승인 범위·TODO 상태·다음 행동·최신 증거 링크 | impl 상단 현재 상태 |
| 실제 변경·구현 결정·단계 수용 사건 | impl 진행 이력 |
| 실행 명령·결과·로그, 리뷰 finding·반영 결과 | impl 검증/리뷰. 길면 별도 기록을 링크 |
| API 명세·외부 반영·승인 대기·운영 후속 | impl 후속 결과 |
| 승인 근거 | impl 현재 상태. 설계 단계에 plan에 남긴 승인은 링크로 참조 |
| Task 번호·작업 목록·상태 한 줄·문서 링크·commit | 로드맵 `roadmap.md`. 상세 내용은 복제하지 않음 |

현재 상태는 새로운 결과로 갱신한다. 과거 이력은 당시 사건으로 남기고 잘못된 기록은 정정 이유를 붙인다. 과거 TODO마다 이후 전체 완료 문구를 덧붙이지 않는다. 최신 PASS·stage 상태는 증거 위치를 가리키며 여러 섹션에 숫자와 상태를 복제하지 않는다.

검증 기록에 실제 결과를 한 번 적고 TODO·진행 이력에는 해당 근거를 연결한다. 실행 전 항목은 계획 또는 미실행으로 표시한다. 시각은 [기록 형식](naming-and-reporting-guide.md)을 따른다.

## 문서 분리

| 위치 | 생성 조건 | 기존 기록에 남길 것 |
|---|---|---|
| `reviews/active/` | 여러 finding·재검토·보안/운영 판단을 독립 추적해야 함 | 결론과 링크 |
| `reports/active/` | 사용자가 요청했거나, 배포·운영·종료 판단을 별도 보존해야 함 | 보고서 링크 |
| `troubleshooting/` | 재사용할 실패 원인·해결법이 있고 기존 기록으로 찾기 어려움 | 증상 요약과 링크 |
| `tech_notes/` | 다음 작업에서도 사용할 확정 정책·기술 판단 | 결정 요약과 링크 |

Critical 한 건, Agent 사용, 백로그 개수만으로 문서를 추가하지 않는다. 짧은 finding은 impl 안에서 해결·추적해도 된다. 별도 문서가 생기면 원문을 두 군데에 복사하지 않는다.

재발 가능한 문제나 재사용할 정책은 기존 노트를 먼저 찾아 갱신하고, 없으면 해당 문서를 작성한다. 일회성 실패나 이미 기록된 규칙이면 impl에 판단을 한 줄 남기면 된다. 외부 vault/문서 저장소 쓰기는 이 로컬 기록 절차만으로 승인되지 않는다.

## 템플릿 사용

[plan](../templates/plan.md), [implementation](../templates/implementation.md), [roadmap](../templates/roadmap.md)를 기본으로 사용한다. 리뷰·보고가 필요하면 [review-record](../templates/review-record.md), [final-report](../templates/final-report.md)를 사용한다. 지식 문서는 [troubleshooting](../templates/troubleshooting.md), [tech-note](../templates/tech-note.md)를 참고한다.

해당 없는 선택 섹션은 생략한다. API·외부 업데이트·지식화 필요 없음 판단은 후속 결과에 한 번 요약하면 충분하다. 공통 작업 규칙, 스킬 원문, 반복 프롬프트와 전체 구현 코드는 복제하지 않는다. 작업자가 필요한 것은 파일/심볼, 입력·출력 계약, 완료 조건과 검증 근거다.
